## The hard problem: AI calls in tests

The pipeline takes 15–60 seconds per run and costs money. You can't hit real AI APIs in every test — that's too slow for a local dev loop and too expensive to run on every push.

The solution: two suites.

**Fast suite** — runs locally and on every CI push:
- AI calls mocked at the HTTP level via Playwright's `page.route()`
- Returns pre-recorded fixture responses
- Full pipeline runs in under 5 seconds
- No credits burned

**Integration suite** — runs manually or pre-deploy, tagged `@integration`:
- Hits real Groq + OpenRouter APIs
- Validates actual pipeline quality, not just the plumbing
- Acceptable to run once before a release, not on every commit

The mocking layer sits at the HTTP level (intercepting requests to `api.groq.com` and `openrouter.ai`), not at the function level. This means the real application code runs — only the external calls are replaced. Bugs in how we call the APIs still get caught.

## Bugs found during manual testing that tests would have caught

Before writing a single Playwright test, manual end-to-end testing on a clean environment found two real bugs.

### 1. BullMQ job ID collision across queues

**What happened:** On a fresh Redis instance, both the transcription queue and chronicle queue start their auto-increment job ID counter at 1. The poll endpoint checks the transcription queue first. When the frontend polls for chronicle job `1`, it finds the already-completed transcription job `1` and resolves immediately — with the wrong result (`audioKey: undefined`). The actual chronicle job keeps running in the background.

**Why it was hard to see:** It only manifests on a completely fresh Redis (clean start, new deploy, volume wipe). In a running system with many jobs, IDs rarely collide. The bug was invisible during development but appeared immediately in production.

**Fix:** Use `randomUUID()` as the job ID for both job types. UUIDs are globally unique regardless of queue.

**What a test would look like:**
```typescript
test('chronicle poll returns the chronicle result, not the transcription result', async ({ request }) => {
  // enqueue transcription job (gets UUID A)
  // enqueue chronicle job (gets UUID B)
  // poll UUID B → should return chronicle result shape
  // assert result has { chronicle, audioKey } not { transcript }
})
```

### 2. Worker crashing on startup — missing env vars

**What happened:** `dotenv/config` in `@chronicler/core` loads `.env` from the current working directory. The worker runs from `apps/worker/`, where no `.env` existed — the file lived at `apps/api/.env`. Worker crashed immediately with `OPENROUTER_API_KEY: Required`.

**Fix:** Moved `.env` to the project root. `dotenv-cli` loads it once at the root level in `dev:all` — child processes inherit the environment.

**What a test would look like:** a startup smoke test that asserts the worker process doesn't exit within the first 2 seconds of launch.

### 3. Redis authentication not configured on Railway

**What happened:** `REDIS_URL` was set to `redis.railway.internal` without credentials. Railway's managed Redis requires a password. Connection failed with `NOAUTH Authentication required`.

**Fix:** Set `REDIS_URL=${{Redis.REDIS_URL}}` in the web service variables — Railway resolves the reference including the generated password.

**What a test would look like:** a health check endpoint that tests Redis connectivity and returns a clear error if it fails, rather than letting BullMQ error silently on every queue operation.

## The LinkedIn angle

"How do you test an AI pipeline without running the AI every time?"

Most developers haven't thought through this. The instinct is to either skip testing entirely ("AI output is non-deterministic anyway") or hit the real API every time ("mocking defeats the purpose"). Both are wrong.

The right answer: mock at the HTTP boundary, not the function boundary. Your application code runs. Your API integration logic runs. Only the external provider call is replaced — and you control exactly what it returns. That gives you fast, deterministic tests that still catch the class of bugs that matter most: wrong request shape, bad response handling, broken job lifecycle.

The non-determinism problem (does the AI write a good chronicle?) is a different question — it belongs in evaluation pipelines, not unit tests.
