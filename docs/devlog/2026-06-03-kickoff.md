## The idea

Friend groups share experiences constantly, but have no good way to preserve them. Photos get buried in camera rolls. Group chats become unreadable walls of noise. The stories that define a group's identity just fade.

**Chronicler** is a mobile app that fixes this. Members record short voice stories about shared events — a weekend trip, a game night, a wild night out. AI transcribes them, then retells the story in a chosen "flavour": a medieval chronicler, a sports commentator, a nature documentary narrator, or an epic fantasy bard. Multiple members can contribute their version of the same event; the app merges their perspectives into a single narrated chronicle. A TTS voice reads it back.

The result is a living, AI-narrated history of the group — as absurd or as epic as the group wants it to be.

I'm building this in public. Not because everything will go right, but because the decisions are the interesting part.

## Why I wrote 8 pages before touching code

Most side projects die in week 6. Not because the idea was bad — because the data model was wrong and it was too painful to fix.

This time I wrote a full Software Design Document before opening a code editor. Not for a team. For me.

The SDD forced decisions I would have deferred until they were expensive:

**Decision 1: Flavour per-group or per-event?**
My instinct was per-group — simpler UI, fewer decisions for the user. The SDD forced me to think about what happens at a game night (comedic flavour) versus a birthday trip (sentimental flavour). They're different events, not different groups. Flavour lives on the event.

**Decision 2: Who can delete recordings?**
Members being able to delete their own recording sounds obvious. But re-running Whisper on audio that was already transcribed costs money for no reason. And once a chronicle has been generated, deleting a recording breaks the record. Owner-only deletion. Decision made in two minutes. Would have been a three-day debate after shipping if I hadn't asked it now.

**Decision 3: How long do we keep audio files?**
Voice recordings are biometric personal data under GDPR and CCPA. Keeping them indefinitely for no reason is a legal liability. The transcript is what we actually need — it's text, it's small, it's far less legally sensitive. Raw audio gets deleted from R2 within 24 hours of successful transcription. A 24-hour retry window exists for failed transcription jobs, then it's gone regardless.

None of these answers are complicated. But without a document forcing me to ask them, I would have shipped the wrong thing and spent a week undoing it.

> The best time to make architecture decisions is when changing them costs nothing.

## The tech stack — and what I ruled out

**Backend: Hono over FastAPI and Express**

Started with FastAPI (Python) because of its async performance and OpenAPI generation. Changed it to Hono (Node.js / TypeScript) before writing a line of code.

Why? I'm more productive in JavaScript. When I'm debugging a BullMQ queue at midnight, I want to be in a language I think in — not one I'm translating into. The performance difference between FastAPI and Hono at Chronicler's scale is irrelevant. The 3am debugging difference is not.

I chose Hono over Express or Fastify for one specific reason: it has a future upgrade path to Cloudflare Workers. Chronicler uses Cloudflare R2 for storage. Running the API at the edge alongside R2 — no egress fees, no cold starts — is not an MVP requirement. But it's a door I didn't want to close. Hono doesn't close it. Express does.

**The full stack:**

| Layer | Choice | Why |
|---|---|---|
| Mobile | Expo (React Native) | Cross-platform iOS + Android with one codebase |
| Backend | Hono + TypeScript | TypeScript-first, minimal overhead, future edge path |
| Database + Auth | Supabase | Managed Postgres, auth, and realtime in one package |
| Storage | Cloudflare R2 | S3-compatible, zero egress fees on audio streaming |
| Job Queue | Redis + BullMQ | Async AI jobs need a real queue, not a setTimeout |
| Transcription | OpenAI Whisper | Best accuracy at this price point |
| LLM | Claude Sonnet 4.6 | Strongest narrative output I tested |
| TTS | OpenAI TTS (tts-1-hd) | Good quality, each flavour gets a different voice |

Every choice trades something. I'll document the tradeoffs as I hit them.

## Why I built the AI pipeline before the mobile app

The riskiest part of Chronicler is not the mobile UI. It is the AI pipeline:

```
voice recording → Whisper transcription → Claude → OpenAI TTS → narrated chronicle
```

If the latency is too high, the app feels broken. If the cost per chronicle is too high, the product isn't viable. If the prompt quality is wrong, the whole value proposition collapses. I can't know any of this from reading documentation.

So the first thing I built was not a mobile app. It was this:

**A 50-line HTML page with a file input that drives the full pipeline.**

Upload an audio file. Wait. Read the AI-narrated chronicle. Click play. The whole loop. No React Native, no auth, no groups, no events. Just the pipeline.

This is Phase 0. The backend code built in Phase 0 is the production backend — nothing gets thrown away. The HTML page is genuinely throwaway. Its only job is to give me real latency numbers, real cost figures, and real output quality across all four flavours before I spend six weeks building a mobile app around something that might not work.

## What the scaffolded code looks like

Phase 0 is live and type-checking clean:

```
apps/api/src/
├── env.ts                    # validates all env vars at startup, crashes clearly if missing
├── lib/
│   ├── redis.ts              # ioredis connection (maxRetriesPerRequest: null — BullMQ requires it)
│   ├── r2.ts                 # Cloudflare R2 via @aws-sdk/client-s3
│   ├── whisper.ts            # audio → transcript via openai SDK
│   ├── claude.ts             # transcript + flavour → chronicle (beta prompt caching enabled)
│   └── tts.ts                # chronicle → audio, each flavour maps to a distinct voice
├── flavours/index.ts         # the four system prompts — this is where quality lives
├── queues/index.ts           # BullMQ typed queues: transcription + chronicle
├── workers/
│   ├── transcription.ts      # download audio → Whisper → delete raw audio from R2
│   └── chronicle.ts          # Claude → TTS → upload to R2
├── routes/pipeline.ts        # /upload, /jobs/:id, /generate, /audio/:key, /flavours
└── index.ts                  # Hono server + web test rig served at /
```

Two processes, two terminals:

```bash
pnpm dev      # API server + test rig at localhost:3000
pnpm worker   # BullMQ workers (transcription + chronicle)
```

One thing I noticed while building: I had to use `anthropic.beta.promptCaching.messages.create()` instead of `anthropic.messages.create()` — prompt caching in SDK v0.27.x lives under the beta namespace. The system prompts (the flavour definitions) are cached per flavour, which means the second time you generate a medieval chronicle, Claude reads the system prompt from cache rather than re-processing it. Measurable cost reduction, no code change needed later.

## Three things I'd tell myself before starting this

1. **Write the SDD first.** Even if it's just for you. Especially if it's just for you.
2. **Validate the AI pipeline before the UI.** The hard problem is not the screen. It is the thing behind the screen.
3. **Pick the language you think in.** Performance differences between good frameworks at early scale are noise. Being able to debug at midnight without friction is signal.
