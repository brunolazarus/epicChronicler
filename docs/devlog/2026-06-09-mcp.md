# MCP Server — Decision Log

**Date:** 2026-06-09
**Phase:** 1 (new)
**SDD version at time of writing:** 0.4
**Status:** Implementation complete — pending first live test in Claude Desktop

---

## What was built

An MCP (Model Context Protocol) server that exposes the Chronicler AI pipeline as callable tools for any AI assistant. Claude Desktop, Cursor, or any MCP-compatible client can now transcribe a voice recording and generate a narrated chronicle without a mobile app or web UI.

Three tools:

| Tool | What it does |
|---|---|
| `transcribe_voice` | Audio → transcript (Groq Whisper) |
| `generate_chronicle` | Transcript(s) + flavour → text chronicle + MP3 audio (Claude + Kokoro) |
| `voice_to_chronicle` | Audio + flavour → everything in one call |

---

## Why MCP before the backend

The original plan had Phase 1 as the full Supabase backend — auth, groups, recordings, chronicles API. That got moved to Phase 2.

**The reason:** the backend produces something exercisable via Postman. The MCP server produces something people can actually use. For a project being built as a public portfolio, "you can talk to it right now from Claude Desktop" is a materially stronger signal than "here are 22 endpoints in a Postman collection."

MCP was also the right architectural forcing function. To expose the pipeline cleanly, the providers had to be isolated from the HTTP server that used to own them. That restructuring was worth doing regardless — it just had a clearer deadline attached to it.

The tradeoff: Phase 2 (backend) is now later, which means the full group experience is further away. Acceptable: the MCP server demonstrates the core product value — the AI pipeline — without needing groups, auth, or a mobile client.

---

## Monorepo restructuring

Before the MCP server could exist, the AI providers needed a home that wasn't `apps/api`. The restructure:

```
Before:
  apps/api/src/lib/          (everything lived here)

After:
  packages/core/             @chronicler/core
    environment, r2, redis
    transcription/ (Groq)
    llm/ (OpenRouter/Claude)
    tts/ (OpenRouter/Kokoro)
    flavours/
    queue-types

  apps/api/                  HTTP server + queue producers only
  apps/worker/               BullMQ consumers only (extracted from apps/api)
  apps/mcp/                  MCP server — no queue, direct provider calls
```

`@chronicler/core` is the dependency shared by all three apps. Swapping a provider is still one line in its `index.ts`.

The MCP server doesn't use Redis or BullMQ. It calls the providers directly. This is intentional — MCP tool calls are synchronous from the client's perspective. The full pipeline (transcribe + LLM + TTS) runs in ~10–15s, comfortably within the 60s timeout of MCP clients.

## The tool separation decision

This was the most deliberate design call in the implementation.

**Option A — one tool, full pipeline:**
`voice_to_chronicle(audio, filename, flavour) → { transcript, text, audio }`

Simple. One call. The obvious first version.

**Option B — two atomic tools + one combined tool (what we built):**
- `transcribe_voice` — does only transcription
- `generate_chronicle` — does only LLM + TTS
- `voice_to_chronicle` — calls both in sequence, returns everything

**Why option B:**

*Composability.* An AI agent using the tools can transcribe first, inspect the transcript, then decide on a flavour — or decide not to generate at all. With a single combined tool, that decision point disappears. The model is forced to commit to a flavour before it has seen the text.

*Multi-speaker support.* `generate_chronicle` accepts an array of transcripts with speaker labels. A workflow where multiple people have recorded their version of the same event requires calling `transcribe_voice` once per recording, then calling `generate_chronicle` once with all the results combined. That workflow is impossible with a single pipeline tool.

*Reuse without re-transcription.* If a group wants the same event retold in a different flavour, they call `generate_chronicle` with the existing transcripts. No audio upload, no Groq call, no cost.

*The combined tool still exists.* `voice_to_chronicle` covers the single-user, single-call use case — voice note in, narrated chronicle out. It's the demo tool, listed first in the tool registry. It composes the two atomic tools internally so there's no logic duplication.

The pattern is: **expose atomic operations, then compose them into convenience wrappers**. The wrappers don't add logic; they reduce call overhead for the common case.

## What we're testing with early MCP users

The MCP server is Phase 1's user testing surface. The audience is technical — developers running Claude Desktop or Cursor — which makes it a filtered sample, not representative of the eventual mobile app user. That's fine. The questions it can answer are the ones that matter right now.

**Hypothesis 1 — Pipeline quality is good enough to share**
Do people who try it send the output to someone else? Forwarding a chronicle — even just screenshotting the text — is the strongest signal. It means the output was entertaining enough that they wanted an audience. If nobody shares it, the flavours or LLM output need work before building the full product around them.

**Hypothesis 2 — Latency is acceptable**
10–15s is a long time if it feels like waiting. Does it feel like processing (acceptable) or broken (not acceptable)? The clearest indicator: do people try it more than once in the same session? One and done usually means the wait killed the experience.

**Hypothesis 3 — Which flavours actually land**
Four flavours exist. One or two will generate noticeably more enthusiasm than the others. That tells us which to feature first in the app and which system prompts need tuning. The flavour distribution in feedback is a signal — don't average it away.

**Hypothesis 4 — Does the concept need explanation?**
If someone picks up the tool and immediately knows what to do with it, the core idea is intuitive. If they ask "so what is this for?", there's a communication problem to solve before the app launches — in onboarding, the store listing, the first-run experience. Better to know that now than after the app is built.

**What we are explicitly not trying to learn here:**
Whether the group mechanic drives retention, whether non-technical users would record voice stories, or whether anyone would pay for it. Those are real questions — they need the full app to answer. Conflating them with MCP feedback would produce the wrong conclusions.

## First live test — trade-offs identified (2026-06-10)

Ran the MCP server through the MCP Inspector against real audio. The pipeline worked end-to-end. The timing breakdown exposed two decisions that need revisiting before the server goes to users.

### TTS: Kokoro via OpenRouter is unreliable

Measured `tts_ms: 205,589` on the first run — over 3 minutes for a short recording. A follow-up benchmark hit a `429 Provider returned 429` immediately. Investigation confirmed: `hexgrad/kokoro-82m` on OpenRouter is hosted by a single downstream provider with no failover. Any load on that one host hits every caller directly. This is a structural limitation, not a transient outage.

**Trade-off logged:** Kokoro was chosen for cost ($0.001/chronicle) and voice quality (flavour-matched voice names). The reliability risk was not visible until live testing. The fix is a provider swap when ready.

**Options evaluated:**

| Provider | Model | Cost/chronicle | Latency |
|---|---|---|---|
| OpenRouter | Kokoro 82M | ~$0.001 | Unreliable |
| ElevenLabs | Flash/Turbo | ~$0.10 | ~75ms |
| OpenRouter | GPT Audio Mini | ~$0.014 | Unknown |

ElevenLabs Flash is the leading candidate — the API key is already in the project, the SDK is installed, and 75ms latency would make the pipeline feel instant. Deferred because voice quality across all four flavours needs to be validated before the swap is committed.

A `scripts/bench-tts.ts` was added to the repo to isolate and benchmark TTS independently of the MCP server.

**The TTS provider is now abstracted behind a model registry** (`packages/core/src/tts/openrouter-models.ts`). Swapping models is one line; voice-per-flavour mappings are co-located with each model entry.

---

### LLM: Claude Sonnet is overkill for style-transfer

Measured `llm_ms: 15,401` for 489 output tokens via `anthropic/claude-sonnet-4.5` on OpenRouter. The task — rewriting a voice transcript in a narrative flavour — is creative style-transfer, not reasoning. A well-structured system prompt reduces the intelligence requirement: the model needs vocabulary and instruction-following, not problem-solving.

**Trade-off logged:** Sonnet was chosen for output quality on a project meant to demonstrate AI capability. The latency cost (15s just for LLM, before TTS) is too high for a real user experience.

**Options evaluated at current OpenRouter pricing:**

| Model | Output cost/M | Per chronicle | Notes |
|---|---|---|---|
| `google/gemini-2.5-flash-lite` | $0.40 | ~$0.0002 | 40× cheaper, quality unvalidated |
| `openai/gpt-4o-mini` | $0.60 | ~$0.0003 | Proven, fast |
| `google/gemini-2.5-flash` | $2.50 | ~$0.001 | Multi-provider, reliable |
| `anthropic/claude-3.5-haiku` | $4.00 | ~$0.002 | Anthropic quality, 7.5× cheaper |
| `anthropic/claude-sonnet-4.5` | $15.00 | ~$0.008 | Current — capability exceeds need |

Decision deferred pending quality benchmark. The same model registry pattern as TTS will be applied to the LLM provider before the swap.

## Remote deployment — Railway + Smithery (2026-06-11)

Getting the MCP server accessible to users outside a local dev environment required two things: an HTTP server that can run remotely, and a distribution mechanism so users don't need to manage credentials themselves.

### HTTP transport

The server now detects whether it's running locally or remotely via the `PORT` environment variable:

- **No `PORT`:** starts in stdio mode — for local clients (Claude Desktop, Cursor direct)
- **`PORT` set:** starts an HTTP server on that port — for remote clients

Both modes use the same tool handlers. The only difference is the transport layer. Railway injects `PORT` automatically, so the same binary runs correctly in both environments without a code change.

Auth in HTTP mode is a simple Bearer token check (`MCP_API_KEY` env var). If the env var isn't set, the server accepts all requests — safe for local, required for remote.

### The distribution problem

A working Railway deployment is a URL plus a secret key. That's fine for personal use, but it's a bad user experience for anyone you want to try the product:

> "Add this server to Claude Desktop — here's the URL, and here's the API key, keep it safe, it's shared."

Shared keys can't be revoked per user, there's no audit trail, and every new user you onboard means distributing a secret. For a demo surface, that's acceptable for a handful of people. It doesn't scale.

### Smithery as the distribution layer

[Smithery](https://smithery.ai) is a registry for MCP servers — analogous to npm, but for tools. Publishing there separates the distribution concern from the infrastructure concern:

- The server runs on Railway (you control it, you pay for it)
- Users discover and install it from Smithery (they authenticate with their own Smithery account)
- Smithery handles OAuth, token refresh, and session management

The `smithery.yaml` at the repo root registers the server with the registry and tells Smithery how to run it. Smithery can host the server itself (running the stdio command as a subprocess) or act as a gateway to a remote deployment.

The user-facing install command becomes:

```bash
# Via Smithery CLI
smithery mcp add brunolazarus/epicChronicler

# Or via Claude CLI directly (OAuth flow triggers automatically)
claude mcp add --transport http chronicler "https://epicchronicler--brunolazarus.run.tools"
```

No API key. No shared secret. The user logs in with their Smithery account and Smithery issues a scoped token.

### How the OAuth handshake works

This was the non-obvious part. When Claude CLI hits `https://epicchronicler--brunolazarus.run.tools` without a token, the Smithery gateway returns:

```
HTTP 401
WWW-Authenticate: Bearer error="invalid_token",
  resource_metadata="https://epicchronicler--brunolazarus.run.tools/.well-known/oauth-protected-resource"
```

Claude CLI follows the `resource_metadata` URL and gets back:

```json
{
  "authorization_servers": ["https://auth.smithery.ai/brunolazarus/epicChronicler"],
  "resource": "https://epicchronicler--brunolazarus.run.tools/"
}
```

From there it initiates a standard OAuth2 browser flow against `auth.smithery.ai`. The user logs in, the CLI receives a token, and subsequent requests to the gateway succeed. The CLI handles all of this automatically — the user just sees a browser window open and then the server connect.

### Current state

| Path | Status |
|---|---|
| Railway HTTP server | ✅ Live — `chronicler-mcp-production.up.railway.app` |
| Smithery registry listing | ✅ Published — `brunolazarus/epicChronicler` |
| OAuth discovery chain | ✅ Working — WWW-Authenticate → resource metadata → auth server |
| OAuth login flow via Claude CLI | 🔄 In progress — `/mcp` command triggers it, browser flow not yet completed |
| Direct Railway connection (bypass Smithery) | ✅ Working — `claude mcp add --transport http` with Bearer token |

The Railway direct connection is being used for immediate testing. Smithery OAuth is the intended path for user distribution once the flow is validated end-to-end.

### The tradeoff logged

Two valid models for distributing a remote MCP server:

**Model A — Direct infrastructure access:** Share the Railway URL + API key. Fast to set up. Works immediately. Does not scale — shared credentials, no per-user revocation, friction every time a new user onboards.

**Model B — Registry + OAuth:** Publish to Smithery, let it manage auth. More setup upfront. OAuth adds a step for the user. But: no shared secrets, tokens are per-user and scoped, and the install command is one line with no credentials to copy.

For a product demo aimed at developers, the difference matters. A developer who can install the server the same way they'd install any other MCP server — one command, browser login — is more likely to actually try it. Friction at the install step is friction before anyone has seen the product.

## Strategy update — what actually happened (2026-06-12)

### The Smithery misunderstanding

The Smithery plan was built on a wrong assumption: that Smithery acts as a proxy to the Railway deployment. It doesn't. Smithery runs your server itself — cloning the repo and starting the stdio process in their infrastructure — and users supply their own API keys through a configuration form.

That's a self-hosting tool, not a demo surface. The goal was to give people a zero-friction way to try the product with our pipeline, using our API keys. Smithery's model is the opposite: users bring their own Groq and OpenRouter accounts. Two API keys required before seeing the product — that's the wrong funnel for the audience we want.

The OAuth flow we spent time on was real and working, but it was solving the wrong problem. The distribution model itself was the mismatch.

### What changed and why

The MCP server is a developer tool. Asking anyone outside that audience to run a terminal command, configure a client, and obtain an API key is asking them to do too much before they've seen anything.

The right surface for non-technical users already existed: the Phase 0 web test rig. It runs the same pipeline — transcription, LLM, TTS — in a browser. No setup. No credentials. Just a link.

The decision: make the web demo the primary user-facing surface and let the MCP server do what it's actually good at — being a credible, deployable developer tool that demonstrates real AI engineering.

### What was shipped

**Web demo polished** (the test rig at the Railway API URL):
- Browser recording via MediaRecorder API — no file upload required
- Copy rewritten for users, not engineers ("Tell the story" not "Generate Chronicle")
- Developer metrics removed from the UI
- MCP callout in the footer for developers who want to go deeper

**MCP server cleaned up:**
- `resources/list` and `prompts/list` handlers added — returns empty lists instead of Method Not Found errors, which matters for scanners and strict MCP clients
- `smithery.yaml` removed — no longer the distribution path
- Architecture diagram and DEPLOY.md updated to reflect Railway as the single deployment target

**Smithery listing** remains on the registry as passive discoverability. Developers searching for MCP servers can still find it. It just isn't the active distribution mechanism.

### The tradeoff that closed this chapter

The MCP server is a portfolio signal, not a product surface. "I built and deployed an MCP server" is a credible line on a LinkedIn post or a resume. It shows understanding of a technology that's genuinely relevant in 2026. That's worth having — but worth showcasing from the web demo, not requiring visitors to install a developer tool to see it.

Both surfaces now serve different audiences correctly:
- **Web demo** → anyone with a link, zero setup, see the product in 30 seconds
- **MCP server** → developers, one command, shows the engineering depth

## Audio input — solving the binary payload problem (2026-06-13)

The first live test against real recordings exposed a fundamental mismatch: `audio_base64` doesn't work for anything larger than ~25KB. A typical voice memo is 2–5MB. The MCP protocol is JSON-RPC — it was never designed to carry binary payloads inline.

The fix: three ways to provide audio, each suited to a different deployment mode.

| Parameter | Transport | How it works |
|---|---|---|
| `audio_path` | stdio (local) | Pass a file path. The server reads it from disk. |
| `audio_url` | HTTP (remote) | Pass a URL. The server fetches it. |
| `audio_base64` | Either | Inline base64. Still supported for small files. |

`filename` is now optional when using `audio_path` — inferred from the path.

### The target user framing

This distinction surfaced a clearer way to think about who uses Chronicler through the MCP server.

For the primary target — a gamer who wants to chronicle their sessions — the right path is Claude Desktop with stdio. They install the MCP server once, point it at their recordings folder, and that's it. No Railway deployment, no API keys, no file upload. They record a voice memo, tell Claude to chronicle it:

> "Chronicle my last session from ~/recordings/session.m4a in epic fantasy flavour"

The model passes the file path. The server reads it. The chronicle comes back. No binary ever touches the MCP protocol.

The Railway HTTP deployment is a different audience — developers and people who don't want to run anything locally. For them, `audio_url` is the right pattern: they upload the file somewhere accessible and pass the URL. It's more setup, but it's also the path that works without installing anything.

Both audiences are real. The tools now serve both correctly.

## Connection reference

**Local (stdio):**

Add to `~/Library/Application Support/Claude/claude_desktop_config.json`:

```json
{
  "mcpServers": {
    "chronicler": {
      "command": "pnpm",
      "args": ["--filter", "mcp", "exec", "tsx", "src/index.ts"],
      "cwd": "/path/to/epicChronicler",
      "env": {
        "OPENROUTER_API_KEY": "your-key",
        "GROQ_API_KEY": "your-key"
      }
    }
  }
}
```

**Remote via Railway (direct — current):**

```bash
claude mcp add --transport http chronicler "https://epicchronicler-production.up.railway.app/mcp" \
  --header "Authorization: Bearer <MCP_API_KEY>"
```

**Required env vars for MCP only:** `OPENROUTER_API_KEY`, `GROQ_API_KEY`. R2 and Redis credentials are not required — the MCP server starts without them.
